# QA 四半期見直し手順 — 指標を見て、検査の重さを直す(QA の QA)

制定: 2026-10-20(レン指示「開発フェーズや規模に応じて必要最低限の QA を判断できる仕組み」の一部)。
基準は `qa-profile-standard.md` §4(昇格・降格)と §7(指標と台帳)。施策の根拠は
`~/yosage-webqa/docs/2026-10-20-qa-upgrade-proposal.md` 1-4(漏れた欠陥台帳と変更失敗率)・4-3(不安定率)。
対象: `~/yosage-webqa/`(S0-S3)と `~/yosage-appqa/`(M0-M3)。道具は `scripts/qa-metrics.mjs`(依存ゼロ・0 円)。

## 0. 一言で

四半期に 1 回、台帳の数字を機械で出し(`qa-metrics.mjs`)、**効いていない検査は軽く・漏れを出した検査は重く**する。
数字は「どの検査を直すか」を決める材料で、**目標にはしない**。初回は 2026-11-05(記録が少ないので確認だけ。判断はしきい値の回数が貯まってから)。

## 2. 手順(この順に)

### 2-1. 集計を出す

```bash
cd ~/qa-standard
# 基盤ごとに 1 回ずつ。期間は前の見直し日の翌日から当日まで(初回 2026-11-05 は --since を付けず台帳の最初から)
node scripts/qa-metrics.mjs --ledger ~/yosage-webqa/ledger --menu ~/yosage-webqa/qa-menu.json --since <前回の翌日> --until <当日>
node scripts/qa-metrics.mjs --ledger ~/yosage-appqa/ledger --menu ~/yosage-appqa/qa-menu.json --since <前回の翌日> --until <当日>
# 傾向を見るときは --since を付けずに全期間でも出す(数字は目標にしない。§3)
```

- `--menu` を付けると、項目ごとの表に「現在の status / frequency」が並び、候補の絞り込み(もう FAIL 可の項目を昇格候補に出さない等)が効く。
- 出力はそのまま `ledger/reports/YYYY-MM-DD-quarterly-metrics.md` に保存する(基盤ごと。非公開の台帳側に置く。`qa-standard` は公開リポジトリなので数字を置かない)。
- 出力の末尾「欠損・注意」を先に読む。**旧様式の行・読めない行・escaped に無い欄・qa-log に無い release_commit・記録の矛盾(false_alarms > findings)・変更失敗率に入れなかった漏れ** は落とさず件数が出る。件数が多いなら、まずそこ(記録の抜け)を直すのがこの日の仕事。
- **`ledger/drills.jsonl`(欠陥埋め込み訓練の台帳。`seeded-defect-drill.md` §9-2)も基盤ごとに読む**。`qa-metrics.mjs` は読まないので人が見る: 訓練の DDP(`found ÷ seeded`)・`missed_types`(落ちた型)・`cleanup_verified` が `false` の行(後始末が未確認=枝が残っている可能性。先に `seeded-defect-drill.md` §10 の確認をする)。訓練は見直しの前に回しておく(`seeded-defect-drill.md`)。台帳が無い・行が無いなら「訓練の記録なし」と報告に書く(黙って落とさない)。

### 2-2. 候補を確かめる(機械の提案を鵜呑みにしない)

出力の「昇格・降格・頻度降格・強化の候補」は **提案**で、`qa-menu.json` は書き換えられていない。候補 1 つごとに次を確かめる。

| 候補 | 機械の条件(暫定の自社基準・基準 §4) | 採る前に人が見ること |
|---|---|---|
| 昇格(所見 → FAIL 可) | 直近 3 回(SKIP を除く)の誤検出 0。`--menu` があるときは status が `warn` / `promoting` の項目だけ(基準 §2 の「扱い」列が「所見→昇格」の項目) | 3 回のうち「指摘 0」だけで通っていないか(検査が発火していない=B6 の疑い)。レポートで実際に指摘を出した回があるか。**基準 §2 の「扱い」列が「所見→昇格」か**(「所見」止まり=`charter`・`design-table-check`・`threat-model`・`perf-web` 等、「記録」「測定」「手順」「前提確認」の項目は昇格しない。機械は status で絞るが、「所見」止まりは status が `warn` なので候補に出る。ここで人が外す) |
| 降格(FAIL 可 → 所見、または設定の見直し) | 誤検出率 50% 超が 2 回連続 | 誤検出の中身が同じ型なら、降格でなく **設定の見直し**(除外・しきい値)で直るか。直るならそちら |
| 頻度降格(毎回 → 四半期、または削除候補) | 直近 8 回で検出 0 かつ平均所要 10 分超 | その項目が守っている事故の型が、ほかの項目で拾えるか。拾えないなら頻度を落とすだけで、削除しない |
| 強化(頻度↑ または FAIL 可に戻す) | 漏れた欠陥の `should_have_caught` がその項目 | 漏れの原因が「項目の設定」か「項目の手順」か「実行していなかった(SKIP・時間上限)」か。SKIP が原因なら時間上限(基準 §3)の方を見直す。**訓練で落ちた型(`drills.jsonl` の `missed_types`)もメニュー強化の材料**(拾う項目が `該当なし` ならメニューに無い型=下の新項目の候補) |

- 候補に無くても、escaped の `should_have_caught` が「該当なし」の漏れが続くなら、**メニューに無い型**なので新しい項目の候補(所見から始める。基準 §4)。
- 出力の「メニューに無い id」(`--menu` があるときだけ出る)は、綴りの誤りか、メニューに足す前の項目。綴りなら台帳を直す(記録の抜けと同じ扱い)。
- 「判定できなかったもの」に `inconsistent`(false_alarms > findings)が出たら、台帳の行を直してから集計し直す。直すまでその項目の候補は出ない。
- 1 回の見直しで足す項目は原則 1 つまで(基準 §6)。同時に足すとどれが誤報を出しているか分からない。

### 2-3. `qa-menu.json` を更新する

採った候補だけ、基盤ごとの `qa-menu.json` の `status` / `frequency` を書き換え、`history` に 1 行足す。

```json
{ "id": "a11y-web", "status": "fail", "frequency": "every",
  "history": [
    { "date": "2026-10-20", "change": "所見で導入" },
    { "date": "2026-11-05", "change": "昇格 warn→fail(直近3回 誤検出0。四半期見直し)" }
  ] }
```

- 書き方は基準 §8。`status` は `qa-menu.mjs` の `STATUSES` の 7 種: `fail`(FAIL 可)/ `warn`(所見)/ `promoting`(昇格中)/ `procedure`(手順)/ `record`(記録)/ `measure`(測定)/ `precheck`(前提確認)。`frequency` は `every` / `quarterly` / `first`(`daily` は無い。本番監視は運用側の日次で、QA は前提確認だけ)。`seeded-drill` は precheck。
- 変えたら `npm test`(`qa-menu.test.mjs`)を回し、メニューが壊れていないことを見る。
- 採らなかった候補は、採らない理由を 2-4 の報告(または保存した集計の末尾)に 1 行ずつ残す(黙って落とさない)。

### 2-4. レンに 5 行で報告する

QA の数字は経営の数字ではないので、噛み砕いて短く。形は固定:

```
1. 期間と件数: 〈前回翌日〉〜〈当日〉、QA 〈n〉件(レベル別の内訳)、漏れた欠陥 〈n〉件(うち即時対応 〈n〉件)
2. 検出率と失敗率: DDP 〈%〉、変更失敗率 (a) 拾えたはずの漏れ 〈n/全リリース〉 (b) 即時対応 〈n/全リリース〉、不安定率 〈%〉
3. 変えたこと: 〈項目 id〉を FAIL 可に昇格 / 〈項目 id〉を四半期へ / 強化〈あり・なし〉
4. 変えなかった候補と理由: 〈項目 id〉の〈候補の種類〉は見送り(〈理由を 1 句〉)
5. 記録の抜け: 旧様式の行 〈n〉・escaped の欠損 〈n〉・記録の矛盾 〈n〉・率に入れなかった漏れ 〈n〉 → 〈どう直したか〉
6. 訓練: 埋めた 〈n〉 / 見つけた 〈n〉(訓練 DDP 〈%〉)、落ちた型 〈…〉、後始末未確認 〈n〉(記録が無ければ「訓練の記録なし」)
```

(〈 〉は集計の出力から埋める。例の数字を置かないのは、出典の無い数字を文書に残さないため)

- 数字に「良い/悪い」の評価語を付けない(次節)。レンに判断を求めるのは、項目の削除とフェーズを下げる変更のときだけ。
- 法務チェックの報告と同じ日に送る。2 通になってよい(混ぜない)。

## 3. 数字は目標にしない(厳守)

- DDP・変更失敗率・不安定率は **傾向と見直しの材料**。「DDP 95% を目指す」のような目標にしない(基準 §7)。
  目標にすると、漏れを台帳に書かない・指摘を数に入れる、という形で数字が良くなり、QA は悪くなる(網羅率と同じゲーム化)。
- しきい値(3 回・50%・8 回・10 分)は **暫定の自社基準**で、出典のある業界値ではない(基準 §4)。
  比べる外の数字で出典があるのは不安定率だけ(Google: 約 0.15%、1% に近づくとテストは価値を失う。施策案 [10])。
  それも「当社もそうあるべき」ではなく「桁が違ったら理由を考える」目安。
- しきい値を変えるときは、この文書と `scripts/qa-metrics.mjs` の `RULES` を同時に直し、改訂履歴(§6)に理由を書く。

## 4. 台帳の様式(記録する側が守ること)

`qa-metrics.mjs` が読む欄。**欄が無い行は捨てずに「欠損」として数える**ので、抜けはこの見直しの日に見える。

### 4-1. `ledger/qa-log.jsonl`(1 QA = 1 行)

従来の `date` / `app` / `level` / `commit` / `result` / `fail` / `warn` / `report` / `note` に、基準 §7 の 3 欄を足す:

| 欄 | 型 | 意味 |
|---|---|---|
| `phase` | 文字列 | その QA を回したときの `QA_PHASE`(`proto` / `build` / `launch` / `scale`) |
| `minutes` | 数値 | QA 全体の所要(分) |
| `items` | 配列 | メニューの項目ごとの記録。要素は `{ "id", "result", "minutes", "findings", "false_alarms" }`。`id` が `build-test` の要素だけ `flaky_tests` / `tests_total` を足す |

`items` の要素:

| 欄 | 型 | 意味 |
|---|---|---|
| `id` | 文字列 | `qa-menu.json` の項目 id(`charter`・`a11y-web` など) |
| `result` | 文字列 | `PASS` / `FAIL` / `WARN` / `SKIP` |
| `reason` | 文字列 | **SKIP の理由**(`time_cap`=時間上限 / `env`=環境 / `not_applicable`=対象なし 等)。SKIP には必ず書く(黙って落とさない)。欄名は `reason` に統一(各基盤の `qa-levels.md` と同じ。`note` には書かない) |
| `minutes` | 数値 | その項目の所要(分) |
| `findings` | 数値 | 出した指摘の数 |
| `false_alarms` | 数値 | そのうち是正不要だった数(メインの検分で決める。0 なら 0 と書く)。**`findings` を超えてはいけない**(超えた行は集計で「記録の矛盾」として数え、その項目の候補判定が止まる) |
| `flaky_tests` | 数値 | **`build-test` の要素だけ**: 再実行で通った(1 回目は落ちた)テストの本数。不安定率の分子 |
| `tests_total` | 数値 | **`build-test` の要素だけ**: その回に実行したテストの本数。不安定率の分母 |
| `note` | 文字列 | 任意(落とした理由・補足) |

- 旧様式の行(2026-10-20 より前)はそのまま残す。書き換えない。
- `fail` / `warn` は従来どおり書く(旧様式の行では「QA で見つけた数 = fail + warn」として DDP に入る)。
- 旧欄 `flaky`(真偽)は 2026-10-20 の初版の名残で、集計では「参考」の件数にだけ出て率には入らない。新しい行には書かない。
- **レン承認で出したら、同じ `commit` で `result: "APPROVED"` の行を 1 行足す**(`fail` / `warn` は 0、`note` に承認日。`items` は空配列でよい)。`CONDITIONAL` のままだと「全リリース」(§5)に数えられず、変更失敗率が実際より大きく出る。モバイル(appqa)の提出は CONDITIONAL → レン承認 → 提出の流れなので特に忘れやすい。

### 4-2. `ledger/escaped.jsonl`(漏れた欠陥 = リリース後に見つかった不具合。1 件 = 1 行)

基準 §7 の欄に `hotfix` を足した様式。1 行目にコメントは置けない(JSON Lines)ので、**定義の単一ソースはこの §4**。各基盤の README(`~/yosage-webqa/README.md`・`~/yosage-appqa/README.md`)は例を 1 行置いて「定義は qa-standard/docs/qa-quarterly-review.md §4」と参照する形にする(2026-10-20 時点で README 側はまだ旧様式のまま: appqa README に `hotfix` が無い・SKIP の理由欄が `note`・severity の語彙が基盤ごとに違う。README を直すのは親の作業)。

| 欄 | 型 | 意味 |
|---|---|---|
| `date` | `YYYY-MM-DD` | 見つかった日 |
| `app` | 文字列 | `daicho` / `albu` / `genzo` / `koe-techo` など(qa-log の `app` と同じ綴り) |
| `found_by` | 文字列 | `レン` / `利用者` / `ロビ` |
| `release_commit` | 文字列 | 不具合を含んだまま出たリリースのコミット(7 桁以上。qa-log の `commit` と照合する) |
| `release_level` | 文字列 | そのリリースの QA レベル(`S2` / `M3` など) |
| `should_have_caught` | 文字列 | 拾うべきだったメニュー項目の id、または `該当なし`(メニューに無い型) |
| `type` | 文字列 | 欠陥の型(`境界ずれ` / `テナント越え` / `fail-open` / `数値入力` / `時限` / `表示` / `仕様` など、事故記録の呼び方で) |
| `severity` | 文字列 | **その基盤のレポート重要度基準に従う**: Web(webqa)= `Blocker` / `High` / `Medium` / `Low`(`templates/qa-report-template.md`)、モバイル(appqa)= `Blocker` / `Major` / `Minor`。集計は語彙ごとに件数を出すだけで、基盤をまたいで合算しない |
| `hotfix` | 真偽 | **即時対応(hotfix・巻き戻し・緊急の再リリース)が要ったなら `true`**。次の通常リリースで直したなら `false`。変更失敗率 (b) の分子 |
| `fixed_commit` | 文字列 or null | 直したコミット。未修正なら `null` |
| `note` | 文字列 | 経緯(1 行) |

例(1 行):

```json
{"date":"2026-11-12","app":"daicho","found_by":"レン","release_commit":"a1b2c3d","release_level":"S2","should_have_caught":"charter","type":"表示","severity":"Low","hotfix":false,"fixed_commit":"e4f5a6b","note":"予約一覧でペット頭数が0のとき「undefined頭」と出る"}
```

- **レンが気づいた不具合は「仕様」と言い張らず全部入れる**(基準 §7)。
- `release_commit` が qa-log に無ければ、集計で「QA を通さずに出た可能性」として出る。QA を飛ばしたなら、それ自体を `note` に書く。qa-log にあっても `PASS` / `APPROVED` の行が無い(CONDITIONAL のまま出た)なら「条件付き・不合格のまま出た可能性」として出る。どちらも変更失敗率には入れない(§5)。
- `release_commit` は 7 桁でも 40 桁でもよい(集計は前方一致で同じリリースに畳む)。
- `build` フェーズ(公開前)でも内部で見つけた分は記録する(基準 §2 `escaped-ledger`: build=記録開始、launch 以降=必須)。

## 5. 指標の定義(集計器と同じ式)

| 指標 | 式 | 注意 |
|---|---|---|
| 欠陥検出率 DDP | QA で見つけた数 ÷(QA で見つけた数 + 漏れた数) | 「QA で見つけた数」は `items` の `findings − false_alarms` の合計。旧様式の行は `fail + warn`(誤検出を引けない)。漏れが 0 件のときの 100% は、記録が始まる前なら意味が無い(出力に注記が出る) |
| 変更失敗率 (a) | QA で拾えたはずの漏れがあったリリース ÷ 全リリース | 「拾えたはず」= `should_have_caught` が `該当なし` 以外。**分子は分母(全リリース)に当たる (app, commit) だけ**を数える(同じリリースを 7 桁と 40 桁で書いても 1 つ)。分母に無い漏れ(qa-log に無い commit・`PASS` / `APPROVED` でない commit・期間外のリリース・`release_commit` 欠損)は率に入れず、件数と理由を別出しする。これで 100% 超は出ない |
| 変更失敗率 (b) | 即時対応が要ったリリース ÷ 全リリース | `hotfix: true`。分子の数え方は (a) と同じ。DORA の変更失敗率の定義に近いのはこちら(施策案 [11]) |
| 全リリース | qa-log の `result` が `PASS` / `APPROVED` の行の (app, commit) の数(期間内) | **暫定の近似**(リリース台帳が無い)。CONDITIONAL は「レン承認待ち」で出ていない可能性があるので数えない。**承認で出したら `APPROVED` の行を足す決まり(§4-1)が守られている前提**で、この近似を使う |
- 不安定率の元データ: `build_test.sh` が 2026-10-20 から `TESTS_TOTAL` と `FLAKY_COUNT`(赤→1 回だけ再実行で通った本数)を出す。実行係はその値を台帳 `items[]` の `build-test` に `tests_total` / `flaky_tests` として写す(走らなかった回・unknown の回は欄を書かない=欠損)。`QA_TESTS=FLAKY` の回の `result` は PASS のまま。
| 項目ごと | 実施回数・SKIP 以外の回数・平均所要・検出・誤検出・誤検出率・不安定・欠損 | 平均所要は `minutes` のある回だけで出し、無い回の数を並べて出す |
