# テストの質の基準 — 全事業共通(単一ソース)

制定: 2026-10-19(レン指示「記事を読んで、QAエージェントの品質を上げる参考になる点があれば取り入れる」)
対象: YOSAGE の全リポジトリの自動テスト(ユニット・統合・E2E)と検査器(`check-*.mjs` / `check_*.py` とその自己テスト)。
読む場面:
- テストや検査器を**書く・直す**とき(開発セッション。`~/.claude/CLAUDE.md` 品質ルールから参照)
- QA エージェント(yosage-webqa / yosage-appqa)が **テスト差分レビュー(S1+/M1+)・変異プローブ(S2+/M2+)** をするとき
- メインが QA レポートの「テストの質」の欄を検分するとき

出典は §6。要点は Khorikov『単体テストの考え方/使い方』と、それを AI 時代に読み直した
ネクスタ社の記事(2026-10-18)から取り、当社の事故記録で裏づけた。

## 0. 一言で

テストの価値は本数ではなく「**壊れたら赤くなり、壊れていなければ黙っている**」信頼で決まる。
AI はテストを数秒で何十本も書くが、価値のないテストも同じ速さで増える。
当社のテストは全部 AI(ロビ)が書く。だから「良いテストを見分ける」仕事を QA の手順として固定する。

## 1. 良いテストの4つの柱(問いの形で使う)

| 柱 | 問い |
|---|---|
| 退行への保護 | 本体を壊したら、このテストは赤くなるか |
| リファクタリングへの耐性 | 振る舞いを変えずに中身を整理しても、通り続けるか |
| 迅速なフィードバック | すぐ終わり、すぐ結果が分かるか |
| 保守のしやすさ | 読めば意図が分かり、動かす準備が少ないか |

価値は4つの**掛け算**。1つでもゼロなら価値はゼロ(本体を壊しても赤くならないテストは、速くて読みやすくても価値ゼロ)。
上の3つは同時に最大化できない。当社の答えも本と同じで、**リファクタリングへの耐性は手放さない**。
壊れていないのに赤くなるテスト(誤報)が続くと赤を信じなくなり、本物の赤まで見逃す。
当社はすでに検査器について「赤を無視する文化」を最悪としている(`~/yosage-content/content-quality-standard.md` §6)。
同じ原則をテスト全体に広げる。

残る調整は「守る範囲の広さ」と「速さ」の配分:
速く何度も回せるユニットテストで業務ルール(判断)を細かく守り、
遅い統合テスト・E2E では「画面からデータまでつながっていること」を要所だけ守る。
どの振る舞いをどの種類のテストで守るかを決めるのが、テストを設計すること。

## 2. 兆候チェック(レビューで見るもの)

テストを読んで「この形は危ない」と気づくための手がかり。3分類で見る。
**見逃しの兆候は見た目がもっともらしく、誤報より気づきにくい**ので最優先で探す。

### 2-1. 誤報の兆候(壊れていないのに赤になる)

| # | 兆候 | 例 |
|---|---|---|
| A1 | 読むだけの処理を何回呼んだかを確かめている | `expect(repo.get).toHaveBeenCalledTimes(1)` |
| A2 | private なフィールド・メソッドの中身や、内部の呼び出し順を確かめている | 中身を整理しただけで赤くなる |
| A3 | 画面の表示(見えるもの・押せるもの)ではなく内部の状態で確かめている | ボタンが画面から消えても緑のまま(記事の実例) |

### 2-2. 見逃しの兆候(壊れても緑のまま)— 最重要

| # | 兆候 | 例 |
|---|---|---|
| B1 | 緑の理由が本体ではなく、テストが用意したスタブの戻り値にある | 本体が呼ばないメソッドにスタブを用意し、モックの既定値で通っている(記事の実例) |
| B2 | 何が渡されても通る | アサーションがない / `expect(true)` / `XCTAssertNotNil` だけ / 「何か書いた」ことしか見ない |
| B3 | 期待値が実装の式を写している | `expect(amount).toBe(unitPrice * qty * (1 - rate))` — 実装が間違っていても一致する |
| B4 | テスト名・コメントの主張を、アサーションでは観測していない | koe-techo S4 QA 所見#6(2026-08-20): 「finish 前に onGrant」という主張はアサーションから独立に観測できず、コードを読んで確認した |
| B5 | 公開の入口(利用者が通る経路)でなく、低レベルの内部 API を直接呼んで通している | 同じ所見#6: `restore()` ではなく `refreshEntitlements()` を直接呼んでいた |
| B6 | 検出器が発火し得ない(fail-open) | 検査器で3回起きた(content-quality-standard §6、2026-08-25)。エラー0件=「すべてOK」と表示されるので、無いより悪い |
| B7 | 境界ちょうど・ちょうど半分を浮動小数で比べている | KAZOERU /bmi/ で 160cm・64.0kg の判定が1段ずれた(2026-10-08)。期待値は打った小数どおりの分数か整数の正解で |
| B8 | 期待値を実装と同じ正規化・丸めの手順で作っている | 全角→半角・NFKC・四捨五入を実装と同じ関数で作ると、その関数の誤りがそのまま期待値になる |

### 2-3. 守る価値がない兆候

| # | 兆候 |
|---|---|
| C1 | 壊れようのない受け渡し(単純な getter / setter / 定数)だけをなぞっている |
| C2 | 赤にも緑にも意味がなく、維持する手間だけが残る(コンストラクタが例外を投げないことだけ、など) |

網羅率はこの兆候を探す**補助**。網羅率が教えるのは「通ったか」だけで、「確かめたか」は現れない
(何も確かめないテストでも 100% になる)。低い場所に気づく合図に使い、目標の数字にはしない
(`~/yosage-webqa/docs/qa-policy.md` §7、`~/yosage-appqa/docs/qa-policy.md` 留意 と同じ)。

## 3. 書くときの決まり(開発セッション)

1. **振る舞いを確かめる。内部の作りは確かめない。** 「この入力ならこの結果」「この操作ならこの表示」「この副作用が外へ出る」が対象。
2. **期待値は仕様から決める。** 定数・早見表・一次情報の制度値・独立した手計算で書く。実装の式や実装と同じ正規化手順を写さない(B3/B8)。
   境界は打った小数どおりの分数か整数の正解で比べる(B7)。
3. **判断は値を受け取って答えを返す形に切り出す。** 判断(料金・空き・権限・丸め・表示の分岐)は DB・時計・乱数・画面に触らず、
   引数だけで答えを返す関数にする。読み書き・通知・画面は「判断の結果に従う薄い殻」にして、統合テストで要所だけ守る。
   切り出した判断には入力→出力だけのテスト(本の「出力値ベース」)が書け、スタブが要らないので B1 が起きない。
   きれいに分けられないとき(判断の途中でデータを読み直す等)は、無理に単体にせず統合テストで結果を確かめる(§4-3)。
4. **テスト・ダブルの使い分け。**
   - **モック**(呼んだ中身まで確かめる)= **外へ出ていく副作用**: メール・LINE 通知・Stripe・外部 webhook・他システムも読む DB への書き込み。
     送った中身(宛先・金額・冪等キー)まで確かめる
   - **スタブ**(値を用意するだけ)= **読むだけの依存**。呼んだ回数は確かめない(A1)
   - **本物を使う** = 自分のアプリだけが使う DB・Durable Object・KV・UserDefaults・ファイル。ローカルの本物で統合テストにする
     (みんなの台帳は `cloudflare:test` の D1/DO で既にこの形。iOS は一時ディレクトリと専用の UserDefaults スイート)
   - **モックの既定値で通るテストを書かない**(B1)。用意した戻り値が実際に使われることを「戻り値を変えたら結果が変わる」形で確かめる
5. **中身を晒さない。** テストを通すために private を public にしない。Swift の `@testable import` は使ってよいが、private の状態を断定する書き方はしない。
   画面は表示・操作で確かめる(A2/A3)。
6. **自分で壊して赤を見てから出す。** 新しいテスト・検査器は、本体(検査器なら入力)を1か所壊して赤くなることを確かめてからコミットする。
   当社の検査器ルール(jikka / tosou の CLAUDE.md「検査器は必ず壊して発火を見ること」・検査器の自己テスト必須)を全テストに広げたもの。
7. **誤報を出すテストは直すか消す。** ユニットテストに再試行(retries)や sleep を足して黙らせない。
   E2E のネットワーク起因の1回再試行(`config/playwright.config.mjs`)は外部要因なので別。
8. **環境のせいで確かめられないときは、理由つきで skip する。** 偽合格にしない(鉄の掟)。形は GENZO の `PurchaseStoreTests.requireProducts()`(XCTSkip に理由と日付)。
9. **網羅率を目標にしない。**(§2 末尾)
10. **判断ロジックを足したらテストも足す。** 認可・課金・料金計算は必須(webqa qa-policy §7)。それ以外も「判断」が増えたのにテストが無ければ QA で WARN になる(§4-1)。

### AI(サブエージェント・自分)にテストを書かせるときの指示文(定型)

> 仕様はこれ(仕様書の該当箇所・期待値の表)。内部の作りではなく振る舞いを確かめること。
> 期待値は仕様から決めた値で書き、実装の式や正規化手順を写さないこと。
> 判断は値を受け取って答えを返す形にし、入力→出力で確かめること。
> モックは外へ出ていく副作用だけ。読むだけの依存はスタブにし、呼んだ回数は確かめないこと。
> 自分のアプリの DB・ストレージは本物(ローカル)で確かめること。
> 書き終えたら本体を1か所壊して赤くなることを確かめ、その diff と結果を報告すること。

出てきたテストに §2 の兆候が無いかを確かめるのは、書かせた側(メイン)の仕事。

## 4. QA での扱い

### 4-1. テスト差分レビュー(S1+ / M1+)

QA エージェントが、基準点からの差分に含まれる**追加・変更されたテスト**(テストファイル・検査器・自己テスト)を §2 の兆候で読む。
- 1件ごとに「ファイル:行・兆候の番号(A1〜C2)・根拠」をレポートの付録に書く
- 重要度: **見逃しが実証された**(§4-2 で本体を壊しても緑)= High(リリース前に直す)。
  兆候のみ = WARN(所見。メインが判断)。誤報の兆候 = WARN
- 差分で**判断ロジックが増えたのにテストが増えていない** = WARN「テストなしの判断」(ファイル:行を列挙)
- 兆候が無ければ「テスト差分レビュー: n本 兆候なし」と書く。差分にテストが無ければ「対象なし」

### 4-2. 変異プローブ(S2+ / M2+)— 本体を壊して赤くなるか

「レビューのたびに本体を壊して赤くなるかを試す人はまずいない」(記事)。人はやらないが、エージェントならできるので手順にする。
- **対象**: 差分で追加・変更された「判断」(受け取った値で答えを返す関数・分岐)。**最大3変異**(1関数1変異)。
  時間は S2 60分 / M2 45分の枠内。足りなければ1変異で打ち切り、残りは「未実施(理由)」と書く
- **場所**: **使い捨ての worktree**(`git worktree add <scratchpad>/mutation-<n> HEAD`)。作業ツリー・開発セッションの枝・コミットには触らない。
  Node は `node_modules` をシンボリックリンクで共有してよい。Xcode は `project.yml` があれば `xcodegen generate`
- **変異の種類**: 比較演算子の反転(`<`→`<=`)・戻り値の固定(`return true`)・分岐の削除・定数の ±1
- **実行**: 該当テストだけ回す(`vitest run -t <名前>` / `xcodebuild test -only-testing:<Target>/<Class>`)
- **判定**: 1つでも赤になれば OK。**全部緑なら「本体を壊しても緑」= 見逃し High**(そのテストは守る力がゼロ)
- **証跡**: 変異の diff と実行結果の要約をレポート付録に。**後始末**: `git worktree remove --force` → `git worktree list` に残っていないことを記録
- 変異できる判断が差分に無ければ「対象なし」

### 4-3. 統合テストを足場にする(設計を直すとき)

判断と読み書きが絡み合ったコードに無理にユニットテストを書くと、モックだらけで整理のたびに赤くなる。手順は3段:
①統合テストで今の振る舞いを守る → ②その安全網の上で判断を切り出す → ③細かい確認はユニットテストへ移し、統合テストは要所だけ残す。
みんなの台帳の S1-b(`shared/data.js` → API 置き換え)はこの形で進める(`check-proto-data.mjs` の 96 項目が①の期待値の表)。

### 4-4. メディアサイト(L1+)

CI はテスト・検査器を走らせるだけで中身は見ない。検査器やテストを足した開発セッションが §3-6(壊して赤を見る)を push 前に自分でやり、
コミットメッセージか HANDOFF に「壊して発火を確認」と書く。

### 4-5. 既存のテストの棚卸し

兆候は新しいテストだけでなく、今あるテストにも見つかる。見つけたら直すか消す(所見として QA 台帳に残す)。
2026-10-19 時点の自動テストは 21 ファイル(みんなの台帳 4・albu 3・GENZO 7・コドモ声シール帳 7)+ 各サイトの検査器。棚卸しは別作業。
